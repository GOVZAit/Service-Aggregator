# Точечная миграция трёх полей отслеживания заказа

## Основание
Production run 36234358144 создал проверенную приватную резервную копию (222767 байт, SHA-256 75f8b2ec3d6d04aff8e3b47a9740a5b5164bca8a8a56c07c68aa998e76c7b926) и остановился: orders существует, но ORM-колонки travel_status, live_location_url и travel_updated_at отсутствуют. В shared/schema.ts они уже требуются, включая default idle.

## Изменение процесса выпуска
Не возвращается автоматический drizzle-kit push. Добавлена ровно одна явно описанная миграция 20260926-orders-travel-columns в отдельном модуле. В подготовке релиза теперь три отдельные фазы: новая проверенная резервная копия → эта точечная миграция → прежняя строгая READ ONLY проверка всех 34 таблиц. Это уточняет прежние документы: подготовка релиза в целом больше не является только чтением; только verifyReadCompatibility остаётся read-only. Новая фаза меняет схему исключительно добавлением перечисленных колонок.

## Гарантии и ограничения
Миграция проверяет физический pg_catalog, обычный непартиционированный orders, PostgreSQL>=11, отсутствие всех трёх полей и совместимость остальных колонок всех таблиц. Частично существующие или отличающиеся типы/default не переписываются — выпуск останавливается. После короткой блокировки таблицы (lock_timeout 3 секунды, statement_timeout 15 секунд) все три ADD COLUMN выполняются одной транзакцией. Любая ошибка приводит к ROLLBACK. DROP/TRUNCATE/DELETE/UPDATE существующих колонок/строк не выполняются. Повтор при уже корректных колонках ничего не меняет.

Для существующих заказов новое travel_status получает предусмотренное моделью idle (поездка не начата); live_location_url и travel_updated_at остаются NULL. Миграция не придумывает фактическую геолокацию, время выезда или завершения и не переписывает основной status, цену, адрес, комментарии или ID заказов.

CI создаёт синтетические данные в изначально пустом одноразовом localhost *_test PostgreSQL. Проверяет сохранность всех старых полей/посторонней таблицы, новые значения по умолчанию, отказ при частичном/неверном состоянии, обязательность проверенной копии и повторный запуск с уже заполненными travel-данными. Рабочая БД этими тестами не используется.

В production требуется новая копия непосредственно перед фазой. Копия на том же сервере не равна off-site backup или полной репетиции восстановления. Миграция может остановиться на занятости таблицы, правах роли, другом расхождении или ошибке резервирования; эти отказы нельзя обходить принудительным push.
