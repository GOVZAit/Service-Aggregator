# Проверяемая публикация без автоматического ORM push

Серверный helper исторически вызывает `npm run db:push`. Оба npm alias db:push и db:check-release теперь запускают `tsx script/check-release-db.ts`, а не drizzle-kit push.

## Текущий порядок подготовки
1. Создать и проверить приватную резервную копию существующей БД.
2. Выполнить единственную явно описанную миграцию `20260926-orders-travel-columns`, если все три поля отсутствуют. Она только добавляет travel_status (default idle), live_location_url и travel_updated_at. Частично применённая/неожиданная схема приводит к отказу. При уже правильных полях — no-op. Подробности и ограничения блокировок: order-travel-migration.md.
3. Выполнить строгую READ ONLY проверку 34 таблиц/261 колонок из shared/database-schema.ts. SELECT ... LIMIT 0 не выводит пользовательские записи. Не сравниваются полностью типы, индексы и ограничения всех таблиц. Ошибки прекращают выпуск.

Подготовка в целом включает указанное добавление колонок и потому НЕ является целиком read-only. Только verifyReadCompatibility — read-only. Автоматическая генерация/исполнение произвольного diff ORM отсутствует. DROP/TRUNCATE/DELETE и переписывание прежних колонок в именованной миграции не выполняются. Существующие startup ensure/seed-функции приложения остаются отдельным механизмом.

## Резервная копия
pg_dump создаёт полный custom-format архив одной БД в `$HOME/.local/state/govza/backups` либо GOVZA_BACKUP_DIR вне release/web-root. Каталог 0700, архив и manifest 0600. Параметры libpq передаются отдельно; пароль — во временном файле 0600, удаляемом после попытки. Строка подключения/пароль/данные архива не выводятся в argv/журнал и не публикуются в GitHub. Неоднозначные/неподдерживаемые параметры не игнорируются.

Любая ошибка/предупреждение pg_dump останавливает выпуск. Проверяются PGDMP, pg_restore --list и полное локальное декодирование в /dev/null без подключения к БД. Manifest содержит размер/дату/SHA-256. Предыдущие копии не удаляются.

CI использует только первоначально пустые localhost *_test базы в одноразовых PostgreSQL-сервисах. Проверяется безопасность копирования, восстановление синтетических данных во второй пустой сервис и сохранность старых полей при точечной миграции. Рабочая БД тестами не восстанавливается и не очищается.

## Публикация и доступ
Production-приложение слушает только loopback и доверяет X-Forwarded-* только локальному reverse proxy. Административный контроль актуальной роли, версии сессии, HTTPS и same-origin сохраняется. Роли пользователей автоматически не меняются.

Workflow допускает только main, требует известных безопасных npm alias, audit без известных уязвимостей, типизацию/build/smoke, HTTPS до отправки релиза и успешную подготовку БД. После активации проверяются HTTPS страниц, совпадение CSS/JS/SW со сборкой, HTTP→HTTPS, 401/no-store для зарегистрированных GET /api/admin/users, /api/admin/summary и /api/admin/providers, сохранение публичных ID автокаталога. Проверочный список маршрутов сверяется с серверными исходниками. Даже при провале сохраняется отчёт без приватных ответов. Это не тест реального авторизованного администратора и не побайтовое сравнение рабочей БД.

## Оставшиеся ограничения
Локальная копия не заменяет off-site/PITR и резервирование загрузок, глобальных ролей, TLS/конфигурации. Шифрование/удалённое хранилище, политика хранения/свободного диска и полная production-репетиция восстановления остаются отдельными работами. Нулевой npm audit не является полным аудитом безопасности ОС/Node.js. Нужна отдельная приёмка на физических телефонах и под реальным администратором.
